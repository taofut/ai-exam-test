# MaterialOps 设计说明（T1 领退 / T2 保障研判）

本文档说明两期实现：第 1～6 章为 T1「单物资与维修套料领退」，第 7～12 章为 T2「备件保障研判」。两期共用同一套台账、权限与时钟，T2 只在 T1 之上增加"读证据 → 调模型 → 人工决策"这一段。文中提到的表、接口、组件均可在仓库中直接检索到，路径以仓库根目录为基准；为免重复，模块路径省略前缀时按以下规则补全——后端模块指 `app/backend/src/materialops/` 下的同名文件，前端组件指 `app/frontend/src/components/` 下的同名文件，契约指 `contracts/schemas/`，测试指 `app/backend/tests/`。

T2 六要素对应关系（便于逐条核对）：7 需求理解、8 方案与流程、9 数据模型、10 接口契约、11 权限与异常、12 AI 方案与失败策略。

# 第一部分 T1 单物资与维修套料领退

## 1. 需求理解

T1 的目标是在既有备件台账上完成两类领用与退回，并保证账实一致：

1. **单物资领用与整单退回**：领用一台设备的备件，扣减对应库存；退回时必须回原仓、回原数量，不允许改量或换仓。
2. **同仓维修套料领用与整单退回**：一次领用 2～5 种不同物资，生成一张父单和完整明细；退回以父单为单位，一次恢复全部明细，不能只退其中一项。

配套要求：记录页要能看到套料完整清单并整单退回；本日统计要按北京时间零点切日、按物资与单位分别展示、套料只按明细计一次；所有写操作必须整体成功或整体不生效。

范围取舍：

| 需求点 | 本期 | 理由 |
| --- | --- | --- |
| 套料原子领用、父子整单退回 | 做 | T1 核心，占 B 板块主要用例 |
| 记录页同页分组展示套料完整清单 | 做 | 契约明确「同页分组或展开即可」 |
| 单物资领用与原单整退 | 做 | 与套料共用同一套台账助手 |
| 本日统计北京时间日界、按物资与单位 | 做 | 预置缺陷，属于必修项 |
| 仓库筛选与权限取交集 | 做 | 预置缺陷，越权筛选不得扩大范围 |
| 独立套料父单管理页、搜索分页、导出 | 不做 | 契约明确不要求，且会拉长前端工时 |
| 行级 `details` 全量错误收集 | 不做 | 契约只要求返回首个明确原因 |
| 幂等键、成功响应重放、跨刷新恢复 | 不做 | 公共契约明确不考；改为版本/状态保护 + 结果未知提示核对 |

## 2. 方案与流程

### 2.1 分层

- 路由层（`app/backend/src/materialops/api/issue_orders.py`、`main.py`）：只做入参结构校验、身份解析、错误码转换，不含业务规则。
- 服务层（`services/issue.py`、`services/kit.py`）：业务判定与事务编排。
- 台账助手（`services/ledger.py`）：单号生成、流水与审计写入、权限矩阵、对外序列化。
- 事务助手（`services/scaffold_helpers.py` 的 `run_atomic`、`cas_stock_delta`）：一次事务内执行回调；库存用条件更新（`WHERE id=? AND version=?`）并让版本 +1。

### 2.2 单物资领用

```text
POST /api/inventories/{id}/issue
  校验 quantity/version/reasonText
  → 事务（BEGIN IMMEDIATE）
      取库存 → 仓库授权 → 库存版本比对 → 余额比对
      → CAS 扣减（on_hand - n，version + 1）
      → 生成 t_material_issue（issue_no=ISS-…，version=0）
      → 写 t_stock_movement（ISSUE，before/after）
      → 写 t_audit_log（MATERIAL_ISSUE）
  → 提交，返回 {issue, inventory}
```

任一环节抛错即整体回滚，库存、单据、流水、审计均不落库。

### 2.3 单物资整单退回

先读单据（校验可见性、是否套料子明细、是否已退），再在一个事务里：

```text
单据条件更新（id + version + returned_at IS NULL）
  → 库存 CAS 加回原数量（version + 1）
  → 单据 version + 1、returned_at 置为同一时刻
  → 写 RETURN 流水与 MATERIAL_RETURN 审计
```

退回不接受新数量、新仓库；请求体带这些字段会被入参校验拒绝。

### 2.4 套料领用

```text
POST /api/material-issue-orders
  结构校验 → 预检（仓库授权、行数 2～5、明细存在且同仓、itemId 不重复）
  → 事务（BEGIN IMMEDIATE）
      建父单 t_material_issue_order（KIT-…，version=0）
      → 逐行：版本比对 → 余额比对 → 库存 CAS 扣减
               → 建明细 t_material_issue（issue_order_id 指向父单）
               → 写 ISSUE 流水
      → 写 KIT_ISSUE 审计
  → 提交，返回 {order, lines, inventories}
```

关键点：套料不循环调用单物资接口（那会产生多次独立提交）。所有行在同一个事务内完成，第二行库存不足时第一行的扣减也回滚。

### 2.5 套料整单退回

```text
读父单 + 明细（权限、状态、行集合校验）
  → 事务（BEGIN IMMEDIATE）
      父单条件更新（version + returned_at IS NULL），version + 1
      → 逐行：库存 CAS 加回 → 明细 returned_at 置同一时刻、version + 1 → RETURN 流水
      → 写 KIT_RETURN 审计
```

父子明细的 `returned_at` 取同一时间戳，因此「父子一致」可直接比较字段。退回行集合必须与原单完全一致（集合比较，不要求输入顺序）；多余的、缺少的、重复的行一律拒绝。

### 2.6 并发与重复提交

- SQLite 下事务起始执行 `BEGIN IMMEDIATE`（`services/ledger.py:16`），先取写锁。否则两个请求各自先 SELECT 再升级写锁会互等，表现为 `database is locked` 的 500。
- 库存更新全部走 `cas_stock_delta`，`rowcount != 1` 即判定版本冲突。
- 单据更新附加 `version = 请求版本` 与 `returned_at IS NULL` 两个条件。
- 结果：同一旧版本的两个请求至多一单成功，另一单返回 `VERSION_CONFLICT` 且无任何部分写入；同一单据并发退回只会增库一次。

### 2.7 前端

- 库存详情页（`app/frontend/src/components/InventoryDetail.tsx`）新增「维修套料领用」区块与弹层。弹层打开时按当前仓库拉取候选库存，行数 2～5，填满最后一行自动补一行；提交前在本地拦截重复物资、非正整数、超库存，服务端仍是唯一判定方。
- 提交失败时弹层不关闭、已填内容保留，并刷新候选库存版本，便于直接重试。
- 记录页（`app/frontend/src/components/IssueList.tsx`）并行拉取父单列表与各自明细，按「维修套料 / 单物资领用」分组；父单卡片展示完整明细与整单退回按钮。
- 领用或退回成功后统一触发 `Workspace` 的刷新计数，库存余额、记录、统计一起更新；请求用 `useRequestScope` 的 lease 做切身份隔离，旧响应不会覆盖新身份的数据。

## 3. 数据模型

T1 复用预置结构，**未新增表、未新增迁移**（Alembic head 仍为 `0006_retire_empty_drafts`）。

| 表 | 关键列 | 本期用途 |
| --- | --- | --- |
| `t_material_issue_order` | `id`、`order_no`（唯一）、`warehouse_id`、`issued_by_id`、`reason_text`、`issued_at`、`returned_at`、`version` | 套料父单 |
| `t_material_issue` | `id`、`issue_no`（唯一）、`inventory_id`、`quantity`、`issued_by_id`、`issue_order_id`（可空）、`reason_text`、`issued_at`、`returned_at`、`version` | 单物资单据与套料明细共用；`issue_order_id` 为空表示普通单 |
| `t_inventory` | `on_hand`、`version` | 库存余额与乐观锁版本，条件更新 |
| `t_stock_movement` | `movement_type`、`business_no`、`quantity`、`before_on_hand`、`after_on_hand`、`actor_id`、`occurred_at` | 每次领用/退回一条，可按单号核对前后数量 |
| `t_audit_log` | `action`、`parameters`、`before_state`、`after_state`、`actor_id`、`occurred_at` | 记录 `MATERIAL_ISSUE`、`MATERIAL_RETURN`、`KIT_ISSUE`、`KIT_RETURN` |
| `t_exam_clock` | `now` | 模拟时间；业务时间统一取该值 |

设计取舍：

1. **不加 `status` 列**：契约规定状态由 `returned_at` 派生（空为 `ISSUED`，非空为 `RETURNED`）。加列会与历史读投影、前端判定形成两个事实源。
2. **明细即真实单据**：套料明细写入 `t_material_issue`，因此统计「套料只按明细计一次」天然成立，不需要额外的汇总表或去重逻辑。
3. **不加索引与唯一键**：`order_no`、`issue_no` 已有唯一约束；现有数据量级下按 `issue_order_id` 过滤无需额外索引。
4. **写路径必须走 ORM**：`services/history.py` 的 `read_history` 是反射只读投影（返回 camelCase 字典），只用于查询，不参与写入。

## 4. 接口契约

所有响应为 JSON；错误响应统一为 `{ "code": "...", "message": "..." }`，HTTP 状态由 `contracts/errors.json` 决定。

| 方法 | 路径 | 请求 | 成功响应 |
| --- | --- | --- | --- |
| `POST` | `/api/inventories/{id}/issue` | `{quantity, version, reasonText?}` | `{issue, inventory}` |
| `POST` | `/api/material-issues/{id}/return` | `{issueVersion, inventoryVersion}` | `{issue, inventory}` |
| `GET` | `/api/material-issue-orders` | `mine`、`warehouseId`、`status` 可选 | `{items: [order]}` |
| `POST` | `/api/material-issue-orders` | `{warehouseId, reasonText?, lines:[{inventoryId, quantity, version}]}` | `{order, lines, inventories}` |
| `GET` | `/api/material-issue-orders/{id}` | 父单 ID | `{order, lines}` |
| `POST` | `/api/material-issue-orders/{id}/return` | `{orderVersion, lines:[{inventoryId, inventoryVersion}]}` | `{order, lines, inventories}` |
| `GET` | `/api/material-issues` | `mine`、`warehouseId`、`itemId`、`status` 可选 | `{items: [issue]}` |
| `GET` | `/api/material-issues/stats` | `period=TODAY`、`groupBy=ITEM`、`warehouseId`、`itemId` 可选 | `{totalQuantity, groups}` |

字段说明：

- `order` 含 `id`、`orderNo`、`warehouseId`、`issuedById`、`issuedAt`、`returnedAt`、`version`、派生 `status` 与 `permissions.canReturn`。
- `lines` 为真实原清单，每行含 `id`、`issueNo`、`issueOrderId`、`inventoryId`、`quantity`、物资信息、`inventoryVersion`、派生 `status`。
- `inventories` 为操作成功后的实际库存，供页面直接刷新余额。
- `stats` 的 `groups` 含 `itemId`、`itemNo`、`name`、`unit`、`quantity`；未指定 `itemId` 时 `totalQuantity` 为 `null`，指定时返回该物资合计。
- `GET /api/material-issue-orders/{id}` 对套料子明细返回 `permissions.canReturn=false`，前端据此引导到父单。

## 5. 权限与异常

### 5.1 权限矩阵

| 角色 | 领用 | 单物资退回 | 套料退回 | 可见范围 |
| --- | --- | --- | --- | --- |
| ADMIN | 可 | 可代退全部仓库内他人单据 | 可代退 | 全部仓库 |
| DISPATCHER | 可 | 可代退本部门及下级仓库单据 | 可代退 | 本部门及下级仓库 |
| ENGINEER | 可 | 仅本人、且原仓当前有权 | 仅本人、且原仓当前有权 | 本部门及下级仓库 |
| REPORTER | 不可（403） | 不可（403） | 不可（403） | 只读 |

补充规则：

- 代退不改变 `issued_by_id`，但 `t_stock_movement.actor_id` 与 `t_audit_log.actor_id` 记录实际操作者，可追溯「谁替谁办」。
- 仓库授权先于业务校验：先判断身份与仓库范围，再判断行数、版本、余额，越权请求不会返回对方的物资名称或余额。
- 仓库、部门筛选只收窄当前权限，不会放大范围（`list_inventories`、`visible_history`、`issue_stats` 口径一致）。

### 5.2 错误码

| 场景 | 错误码 | HTTP |
| --- | --- | --- |
| 缺少身份 / 员工号不存在 | `AUTH_REQUIRED` / `AUTH_INVALID` | 401 |
| 越权仓库、越权单据、只读角色写入 | `NO_PERMISSION` | 403 |
| 库存不存在 / 单据不存在 / 父单不存在 | `INVENTORY_NOT_FOUND` / `ISSUE_NOT_FOUND` / `ISSUE_ORDER_NOT_FOUND` | 404 |
| 行数不在 2～5、重复物资、混仓、退回行集合不符 | `KIT_LINES_INVALID` | 400 |
| 数量不是正整数 | `QUANTITY_INVALID` | 400 |
| 统计参数非法、状态参数非法 | `QUERY_ARGUMENT_INVALID` | 400 |
| 版本过期（库存或单据） | `VERSION_CONFLICT` | 409 |
| 余额不足 | `STOCK_INSUFFICIENT` | 409 |
| 单据已退回 | `ISSUE_ALREADY_RETURNED` | 409 |
| 直接退套料子明细 | `KIT_RETURN_REQUIRED` | 409 |
| 请求体结构非法 | `VALIDATION_ERROR` | 422 |
| 未预期异常 | `INTERNAL_ERROR` | 500 |

异常处理约定：

- 业务错误统一抛 `AppError(code, message)`，由全局处理器转成上表状态码，不吞异常、不把堆栈或请求体回给客户端。
- 事务内任一失败整体回滚；失败后页面保留已填内容，仅提示原因。
- 写请求没有收到响应（断网、超时）时不提示「重试」，而是提示到「我的领用」核对结果，避免重复扣库。

## 6. AI 方案与失败策略

T1 是纯规则与事务的业务，**不调用任何模型**：数量、余额、版本、权限全部由服务端确定性计算。本期不做以下事情，也不以模型输出替代：单号生成、库存计算、权限判定、超量放行。

模型能力只出现在 T2（保障建议）与 T3（调拨对话），本期未实现，因此模型不可用、超时、返回非法 JSON 都不会影响 T1 的领退链路。

开发过程使用 AI 的方式与边界：

1. **分阶段推进**：按需求分析、模型确认、后端接口、前端接线、缺陷修复、静态审查、交付文档七个阶段逐段确认，每段只做一件事，避免一次性生成整个模块。
2. **上下文分档**：每阶段首轮给出目标、范围、验收标准与必要的接口样例；后续轮只引用已有结论，不重复粘贴工程代码。
3. **最小改动**：发现缺陷时只改触发问题的那几行（例如套料弹层的空行处理、写失败的提示文案），不重写模块。
4. **人工守门**：需求取舍、权限矩阵、错误码映射由人确认；AI 产出的每条断言都用真实接口跑过（`app/backend/tests/test_timed_kit_issue.py` 与浏览器实测）。

失败与降级策略：

| 失败类型 | 处理 |
| --- | --- |
| 库存或单据版本过期 | 返回 `VERSION_CONFLICT`，页面提示刷新后重试，不做自动重发 |
| 任一行余额不足 | 整个套料回滚，返回 `STOCK_INSUFFICIENT`，已填清单保留 |
| 单据已退回 | 返回 `ISSUE_ALREADY_RETURNED`，不重复入库 |
| 请求结果未知（未收到响应） | 提示到记录页核对，由人决定是否重新提交 |
| 服务端未预期异常 | 返回 `INTERNAL_ERROR`，事务整体回滚，库存与单据不变化 |

# 第二部分 T2 备件保障研判

## 7. 需求理解

T2 要回答一个具体问题：**这个仓、这个物资、现在该不该补、补多少、依据是哪一句原文**。它与 T1 的分工是——T1 动账（扣减、退回），T2 只出建议和记录人工决定，不写库存。

一次分析需要的三类输入与两类输出：

| 类别 | 内容 | 来源 |
| --- | --- | --- |
| 实时数量 | 当前余额、库存版本、补货点、目标库存 | `t_inventory`、`t_item` |
| 本日消耗 | 当日该仓该物资的全部领用量（含同事领用，退回不抵扣） | `services/queries.py` 的 `issue_stats` |
| 维护依据 | 状态为 `ACTIVE`、部门可见、`itemNos` 适用当前物资的资料原文 | `resources/demo/knowledge-baseline.json` |
| 建议 | 数量、理由、置信度、引用（编号/标题/版本/连续原文） | 模型输出，服务端逐项校验 |
| 决策 | 采纳 / 修改后采纳 / 拒绝，含复核确认、决定人、决定时间 | 人工通过接口提交 |

四条硬约束，直接对应验收用例：

1. **统计范围不能张冠李戴**：`issueStats` 固定为「该仓 + 该物资」，不因调用者换人而变，也不跨仓累加。
2. **通用资料不是维护依据**：只有通用规则、没有该物资维护资料时，仍要列出"缺依据"的复核项，不许静默给一个数字。
3. **引用必须可回查**：`docId` 必须是本次送检的资料，`title`、`version` 必须一致，`quote` 必须是正文里的连续原文；伪造、改写、拼接一律不认。
4. **模型出错不能变成 500**：超时、网关失败、非法 JSON、结构或引用不符，都要给一个标注过的备用建议，由人决定。

范围取舍：

| 需求点 | 本期 | 理由 |
| --- | --- | --- |
| 单次分析返回建议并落 `PENDING` 记录 | 做 | T2 主流程，B 板块主要用例 |
| 知识可见性、适用性、停用过滤 | 做 | 契约明确"仅有效且有权资料可进模型" |
| 引用三要素服务端校验 | 做 | 防止伪造依据进入决策 |
| 本日统计固化仓库与物资 | 做 | 复用 T1 已修正的统计口径 |
| 三种决定 + 重复决定拒绝 | 做 | 决策链路的完整闭环在"记录"这一步 |
| 必须复核时强制 `reviewed=true` | 做 | 复核结果落库，不向客户端取信 |
| 模型失败降级 + 明确原因 | 做 | 契约 F08，五类故障走同一路径 |
| 刷新后按 `callId` 查看结论 | 做 | 记录可追溯，不依赖前端状态 |
| 独立知识列表/详情/检索页 | 不做 | 页面只需展开本次引用原文 |
| 向量检索、索引热更新、topK | 不做 | 知识为预置只读文件，规模不需要 |
| 草稿表、审批流、多级签核 | 不做 | 契约只要求单次人工决定 |
| 幂等键与响应重放 | 不做 | 公共契约明确不考，用状态机与版本保护替代 |
| 模型自动重试、多来源部分成功 | 不做 | 会把一次请求变成不确定时长的多次调用 |
| 采购准确率、唯一最优补货量 | 不做 | 非确定性目标，无法作为断言 |

## 8. 方案与流程

### 8.1 分层

- 路由层 `app/backend/src/materialops/api/advice.py`：身份与仓库范围校验、请求体白名单、`jsonschema` 校验，不含业务规则。
- 编排层 `services/advice.py`：取证 → 检索 → 渲染提示词 → 调模型 → 校验 → 落库 → 组装响应，以及三种决定。
- 知识层 `services/knowledge.py`：只读文件的可见性/适用性过滤、复核项生成、引用校验。
- 复用件：`services/queries.py` 的 `get_inventory`、`issue_stats`；`services/access.py` 的 `authenticate`、`require_manager`、`department_scope`；`services/clock.py` 的 `now`、`iso`；`ai/client.py` 的 `complete_json`；`ai/prompts.py` 的 `render_prompt`。

### 8.2 分析流程

```text
POST /api/inventories/{id}/ai-replenishment
  鉴权（X-User → authenticate → require_manager → get_inventory，先定仓库范围）
  → 单 session 取证（库存/物资/仓库/本日统计/模拟时间/部门范围）
  → 知识过滤（ACTIVE + 部门可见 + itemNos 适用）→ 拆维护资料与通用规则
  → 生成复核项（缺维护依据 / 周期表述互斥）
  → 渲染 replenishment-v1（inventory、issue_stats、knowledge、output_schema）
  → 调模型（超时/网关/非法 JSON → 降级）
  → 校验建议（实体与库存一致、字段符合 schema、引用可回查、数量 0～500 整数）
  → 落 t_ai_call_log（decision=PENDING，context 存证据与复核结论）
  → 返回 200（含 degraded / requiresHumanReview / reviewItems）
```

关键点：**取证在一个 session 内完成**，库存余额、版本、本日统计、`asOf` 取自同一时刻，避免"统计按旧余额、建议按新余额"的错位；统计参数显式传 `warehouseId` 与 `itemId`，不依赖调用者身份推导。

### 8.3 知识过滤

`knowledge.applicable(departments, itemNo)` 逐条判断，四个条件同时成立才进入候选：

| 条件 | 判定 | 不满足时 |
| --- | --- | --- |
| 状态有效 | `status == "ACTIVE"` | 直接排除，不告知模型 |
| 部门可见 | `deptId is None`（公共）或 `deptId in department_scope` | 直接排除 |
| 物资适用 | `itemNos` 含当前物资编号 | 归入通用资料，不作维护依据 |
| 非通用 | `itemNos` 为空 | 归入通用规则，只作背景 |

`itemNos` 是硬边界：即使正文提到某物资，只要编号不在列表里也不算适用，避免关键词把资料"扩大解释"到别的物资。

### 8.4 引用校验

`knowledge.validate_references` 逐条比对，任一项不符即判本次输出不可用：

1. 字段集合必须恰为 `docId/title/version/quote`，多一个少一个都不接受。
2. `docId` 必须在本次送检集合内（越权或不存在的资料不可能被引用）。
3. `title`、`version` 必须与本次送检一致（防止引用同名旧版）。
4. `quote` 必须非空，且是 `content` 的连续子串（`quote in content`），改写、拼接、跨段摘录都会被拒。

校验失败不返回错误码，而是走降级：模型建议整体弃用，改用库存差额的备用值，并在 `reviewItems` 写明原因。

### 8.5 复核判定

`requiresHumanReview = bool(reviewItems)`，`reviewItems` 只有三个来源：

| 来源 | 触发条件 | 提示内容 |
| --- | --- | --- |
| 缺维护依据 | 该物资没有任何适用维护资料，仅有通用规则 | 列出物资编号，说明"仅通用规则，须人工核实" |
| 明确冲突 | 同一物资的多篇有效资料正文出现互斥周期表述（如「每月」对「每季度」） | 列出资料标题与冲突的周期词 |
| 模型降级 | 超时、网关失败、非法 JSON、结构或引用不符 | 写明失败类型与"已给备用建议，须复核" |

冲突只认周期表述这一种可机械判定的形式，不做语义推理；也不因为"有多篇资料"就一律要求复核——正常采纳场景必须能直接走通。

### 8.6 人工决定

```text
POST /api/inventories/{id}/ai-replenishment/{callId}/{adopt|adopt-edited|reject}
  鉴权 → action 合法 → 请求体字段白名单 → 记录存在且属于该库存
  → 已决定？409 AI_DECISION_CONFLICT
  → 非 reject：必须复核时 reviewed 必须为 true；库存版本必须等于分析时版本
  → 组装最终计划（原建议不改写）
  → 条件更新（WHERE id=? AND decision='PENDING'）：decision、final_suggestion、context.decisionMeta
  → rowcount != 1 → rollback + 409（并发重复决定）
  → 返回完整结论
```

- `adopt`：`final_suggestion = original_suggestion` 的副本，`decision = ADOPTED`。
- `adopt-edited`：只覆盖 `suggestedQuantity` 与 `reason`，其余字段（含引用、置信度）沿用原建议，`decision = ADOPTED_EDITED`。
- `reject`：`final_suggestion` 保持空，`decision = REJECTED`，`context.decisionMeta.reviewed` 为 `null`。
- 决定不写库存、不生成单据：T2 的产出是"计划"，执行仍走 T1 的领用接口。

### 8.7 前端

- `InventoryDetail.tsx` 在 `permissions.canAnalyze` 为真时挂载 `AiPanel`；ENGINEER / REPORTER 看不到面板，接口同时拒绝。
- 面板展示建议数量、理由、置信度、`备用建议` / `需人工复核` / `待人工决策` 角标；`ai-issue-stats` 展示本日领用量、统计范围与分析时的余额、补货点、目标库存。
- 模型返回 `needHuman=true` 而服务端判定无需强制复核时，`ai-need-human` 提示"模型建议人工判断，可直接采纳或修改后采纳"——把模型意见展示出来，但不越过契约 F05 的三种强制情形。
- `ai-knowledge-source` 用原生 `<details>` 展开本次送检的每篇资料（标题、版本、通用标记、正文），对应"可查看引用原文"，不新建知识页。
- 三种决定：直接采纳需先勾选复核（必须复核时按钮置灰）；修改后采纳弹窗内同样有复核勾选（`ai-reviewed-edit`），避免遮罩内无入口；拒绝无需复核。
- 库存版本变化时提示"库存已更新，请重新分析后采纳"，两个采纳按钮置灰，拒绝仍可用。

## 9. 数据模型

**未新增表、未新增迁移**。T2 复用 baseline 建立的 `t_ai_call_log`，其 14 列已覆盖分析、建议与决定所需信息（`app/backend/src/materialops/models.py` 的 `AICallLog`）。

| 契约字段 | 存储位置 | 说明 |
| --- | --- | --- |
| `callId` | `id` | 自增主键，页面与接口的稳定标识 |
| `inventoryId` | `inventory_id` | 与路径参数比对，防止串记录 |
| `inventoryVersion` | `inventory_version` | 分析时的库存版本，采纳前与当前值比对 |
| `suggestion` | `original_suggestion`（JSON） | 模型原建议，任何决定都不改写 |
| `finalSuggestion` | `final_suggestion`（JSON） | 采纳后写入；拒绝保持 `NULL` |
| `decision` | `decision` | 插入即 `PENDING`，不依赖列默认值 |
| `degraded` / `requiresHumanReview` / `reviewItems` | `context.review` | 落库而非现算，保证重读与采纳校验同口径 |
| `reviewed` / `decisionById` / `decisionAt` | `context.decisionMeta` | 契约允许的位置，避免加列 |
| 证据 | `context.inventory` / `issueStats` / `knowledge` | 知识存全文，供引用回查与页面展开 |
| 审计 | `model`、`prompt_version`、`duration_ms`、`input_tokens`、`output_tokens`、`raw_output`、`failure_reason`、`created_at` | 降级路径也写真实值，便于定位 |

`context` 的实际结构：

```json
{
  "inventory": {"id": 8101, "warehouseId": 4101, "itemId": 5101, "itemNo": "PWR-24-A",
                "unit": "个", "onHand": 10, "version": 0, "reorderPoint": 5, "targetStock": 20},
  "issueStats": {"period": "TODAY", "quantity": 12, "scope": "仓库4101/物资5101",
                 "asOf": "2026-10-12T02:00:00Z"},
  "knowledge": [{"docId": 10101, "title": "24V电源模块维护要求", "version": 1,
                 "general": false, "content": "…"}],
  "review": {"degraded": false, "requiresHumanReview": false, "reviewItems": []},
  "decisionMeta": {"reviewed": true, "actorId": 7102, "at": "2026-10-12T02:05:00Z"}
}
```

设计取舍：

1. **不加计划表**：公共契约明确 T2 待办计划保存在 `final_suggestion` 与 `decision` 内，加表会与 T1 的领用单据形成两个事实源。
2. **不复活草稿表**：`t_replenishment_draft` 已由迁移 `0006_retire_empty_drafts` 清理，T2 不提供草稿读写。
3. **原建议只读**：修改后采纳写 `final_suggestion`，`original_suggestion` 保留，审计能看出"人改了多少"。
4. **复核结论落库**：`context.review` 是采纳时是否强制复核的唯一依据，客户端提交的标记不参与判断。
5. **不加索引**：查询只有主键与 `inventory_id` 过滤，当前数据量级不需要额外索引。

## 10. 接口契约

响应统一为 JSON；错误为 `{ "code": "...", "message": "..." }`，HTTP 状态见 `contracts/errors.json`。分析响应由 `contracts/schemas/advice-response.schema.json` 校验，修改后采纳的请求体由 `contracts/schemas/advice-edit.schema.json` 校验，模型输出结构由 `contracts/schemas/ai-replenishment.schema.json` 校验。

| 方法 | 路径 | 请求 | 成功响应 |
| --- | --- | --- | --- |
| `POST` | `/api/inventories/{id}/ai-replenishment` | 无请求体（可空对象） | 分析结果（见下） |
| `POST` | `/api/inventories/{id}/ai-replenishment/{callId}/adopt` | `{reviewed?}` | 分析结果，`decision=ADOPTED` |
| `POST` | `/api/inventories/{id}/ai-replenishment/{callId}/adopt-edited` | `{suggestedQuantity, reason, reviewed}` | 分析结果，`decision=ADOPTED_EDITED` |
| `POST` | `/api/inventories/{id}/ai-replenishment/{callId}/reject` | 无（空对象亦可） | 分析结果，`decision=REJECTED` |
| `GET` | `/api/inventories/{id}/ai-replenishment/{callId}` | — | 分析结果 |

分析结果字段：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `callId` | int | 本次分析记录 ID |
| `inventoryId` / `inventoryVersion` | int | 库存与快照版本 |
| `suggestion` | object | `warehouseId`、`itemId`、`suggestedQuantity`、`reason`、`confidence`、`needHuman`、`knowledgeReferences` |
| `degraded` | bool | 是否走了降级路径 |
| `requiresHumanReview` | bool | 是否必须先复核 |
| `reviewItems` | string[] | 复核原因，逐条可读 |
| `decision` | string | `PENDING` / `ADOPTED` / `ADOPTED_EDITED` / `REJECTED` |
| `context` | object | `inventory`、`issueStats`、`knowledge`、`review`、`decisionMeta` |
| `usage` | object | `inputTokens`、`outputTokens`、`model` |
| `finalSuggestion` | object \| null | 采纳后的最终计划 |
| `reviewed` | bool \| null | 决定时是否确认复核；拒绝为 `null` |
| `decisionById` / `decisionAt` | int \| null / string \| null | 决定人与时间（`Z` 结尾） |

约定：

- 决定请求体只接受白名单字段：`adopt` 只收 `reviewed`，`adopt-edited` 只收 `suggestedQuantity`、`reason`、`reviewed`，`reject` 不收任何字段。夹带其他字段返回 `422 VALIDATION_ERROR`，防止客户端伪造 `needHuman`、`confidence` 等结论性字段。
- `reviewed` 必须是布尔值（`type(x) is bool`），字符串 `"true"` 不接受。
- `adopt-edited` 的数量为 0～500 的整数，理由非空；引用不由客户端提交，沿用本次分析的真实引用。
- `GET` 与决定接口都以路径中的 `inventoryId` 与记录的 `inventory_id` 比对，不匹配返回 `404 AI_CALL_NOT_FOUND`。

## 11. 权限与异常

### 11.1 权限矩阵

| 角色 | 发起分析 | 采纳 / 修改采纳 / 拒绝 | 读取记录 | 可见知识范围 |
| --- | --- | --- | --- | --- |
| ADMIN | 可 | 可 | 可 | 全部仓库 + 公共资料 |
| DISPATCHER | 可 | 可 | 可 | 本部门及下级仓库 + 公共资料 |
| ENGINEER | 不可（403） | 不可（403） | 不可（403） | 不适用 |
| REPORTER | 不可（403） | 不可（403） | 不可（403） | 不适用 |

补充规则：

- 三个入口统一先执行 `authenticate` → `require_manager` → `get_inventory`，权限与仓库范围先于入参校验：ENGINEER 调非法 action 得到 `403` 而不是 `400`。
- 知识可见性另按 `department_scope` 判断，与库存仓库范围同源；越权资料不会被检索、也不会出现在 `context.knowledge`。
- 决定不改变库存，因此不涉及跨角色代操作；`decisionMeta.actorId` 记录实际操作者。

### 11.2 错误码

| 场景 | 错误码 | HTTP |
| --- | --- | --- |
| 缺少身份 / 员工号不存在 | `AUTH_REQUIRED` / `AUTH_INVALID` | 401 |
| 非管理员/协调员、越权仓库 | `NO_PERMISSION` | 403 |
| 库存不存在 | `INVENTORY_NOT_FOUND` | 404 |
| 分析记录不存在或与库存不匹配 | `AI_CALL_NOT_FOUND` | 404 |
| 不支持的 action、非法查询参数 | `QUERY_ARGUMENT_INVALID` | 400 |
| 请求体字段非法、夹带结论性字段、数量越界、理由为空 | `VALIDATION_ERROR` | 422 |
| 已决定后重复决定、并发重复决定 | `AI_DECISION_CONFLICT` | 409 |
| 必须复核但未确认 | `HUMAN_REVIEW_REQUIRED` | 409 |
| 分析后库存版本变化仍采纳 | `VERSION_CONFLICT` | 409 |
| 未预期异常 | `INTERNAL_ERROR` | 500 |

异常顺序固定为：身份（401）→ 角色与仓库（403）→ action 与请求体（400/422）→ 记录（404）→ 状态（409 重复决定）→ 复核（409）→ 版本（409）。模型侧的失败不进入这张表，全部转为 `200` + `degraded=true`。

## 12. AI 方案与失败策略

### 12.1 提示词与输出约束

- 提示词为 `app/backend/prompts/replenishment-v1.json`，变量固定四个：`inventory`（库存快照）、`issue_stats`（本日统计）、`knowledge`（本次送检资料）、`output_schema`（建议的 JSON Schema）。`render_prompt` 会校验变量集合，缺一个即报错，避免模板与代码脱节。
- 系统提示明确边界：只返回 JSON、不执行业务操作、实时数字只用本次查询、资料中的旧盘点不代表当前余额、引用只能用本次真实编号与连续原文、不编造、不声称已采纳或到货；并说明服务端仍会校验实体、数量、引用与权限。
- 业务口径写进 `task`，而不是留给模型自由发挥：补货点为触发线、目标库存为上限——`onHand < reorderPoint` 时 `suggestedQuantity = targetStock − onHand`（0～500 整数），`onHand ≥ reorderPoint` 时取 `0` 并说明未触发；本日原始领用量只作需求信号，不得再次从余额扣减、不得跨仓累计；理由须逐项写明余额、补货点、目标库存、本日领用量四个数字。加这条的直接原因：无口径时真实模型对同一库存连续给出 `0` 与 `10` 两种结论，加口径后连续两次一致。
- 模型输出的 JSON 由服务端逐层校验：`json.loads` → 顶层为对象 → `warehouseId`/`itemId` 与当前库存一致 → 不含 `references`（本版不引用历史单据）→ 引用逐条回查 → 字段与数量符合 `ai-replenishment.schema.json`。任何一层失败即 `AdviceInvalid`，转降级。

### 12.2 失败与降级

| 失败类型 | 表现 | 处理 |
| --- | --- | --- |
| 模型超时 | `ModelTimeout` | `200` + `degraded=true`，备用数量，`failure_reason` 记超时 |
| 网关/服务不可用 | `ModelError` | 同上，`reviewItems` 写明原因 |
| 非 JSON / 非对象 | `AdviceInvalid` | 同上，弃用模型输出 |
| 实体不符（仓库或物资被改） | `AdviceInvalid` | 同上，不采纳模型给的实体 |
| 引用伪造、版本不符、非连续原文 | `ReferenceInvalid` | 同上，引用整体清空 |
| 数量越界（如 501）或字段缺失 | `AdviceInvalid` | 同上，不裁剪、不猜测 |
| 库存不存在或越权 | `AppError` | `404` / `403`，不降级（无证据可给） |
| 数据库异常 | 未捕获异常 | `500 INTERNAL_ERROR`，不落半条记录 |

备用建议的计算是确定性的：`max(0, min(500, targetStock - onHand))`，`confidence=0`、`needHuman=true`、引用为空，理由写明"模型未返回可用结果 + 差额口径 + 须人工核实"。这样评委在无密钥环境下也能看到完整链路，而不会看到一个 502。

### 12.3 为什么不在本期做

- **不重试、不切备用模型**：一次请求的耗时上限要可预期，重试会把 3 秒变成 9 秒，且失败原因会混在一起。
- **不让模型动账**：T2 只产出计划，采纳也不写库存；库存变更仍由 T1 的领用接口在事务内完成，避免"AI 建议直接扣库"这类越权。
- **不做语义冲突判定**：只比较可机械验证的周期表述，宁可漏报交给人，也不误报把正常单子全部打回复核。
- **不做向量检索与打分**：知识是预置小文件，按部门与物资编号过滤已足够；引入索引会让"本次送检集合"与"引用校验集合"出现两个来源，反而削弱可回查性。

### 12.4 开发过程中 AI 的使用边界

1. 按需求分析、模型确认、后端接口、页面挂载、缺陷修复、静态审查、交付文档分七段推进，每段由人确认后再进入下一段。
2. 每段只提供当前任务需要的契约片段与工程风格结论，不重复粘贴整个模块的代码。
3. 模型故障路径用工程内置的 `X-Model-Fault` 夹具驱动，五类失败各跑一遍真实接口，不靠阅读代码推断。
4. 需求取舍（复核触发条件、降级返回码、统计口径）由人拍板；AI 产出的断言都用真实接口跑过，落在 `tests/test_timed_advice.py`。
